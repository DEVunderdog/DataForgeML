# dataforge

`dataforge <command> [--flag value ...]` runs one command per process and prints one JSON value on stdout, on success and on failure alike. Commands keep their state as Handles, strings such as `frame_7f3a9c2e`, stored in the Workspace (`.dataforge/` in the working directory). A Handle is write-once: a command that writes makes a new Handle, and every older Handle stays readable.

## The Handle chain

Each step reads the Handle before it and writes a new one:

1. `load` a CSV → frame.
2. `profile` the frame → profile. Every later step reads the profile, never the raw rows.
3. `split` the profile → a `test` frame and `folds`, each with a `train` frame.
4. `route` the profile → routing: one imputation strategy per column.
5. `resolve-recipe` the routing → recipe, listing the units to fit.
6. `fit-unit` once per listed unit, on a fold's `train` frame → unit.
7. `compose-imputer` the recipe and its units → imputer.
8. `impute` any frame with the imputer → filled frame.
9. `evaluate-imputation` the filled frame against the profile → c2st report.

The `describe-*`, `missingness`, `top-associations`, `value-summary`, `explain-routing` and `query-frame` commands read a Handle and write none. `list-handles` finds Handles made earlier, after a restart or by a sub-agent sharing the Workspace.

## Reading a command

- `dataforge <command> --help` gives every flag with its default and range, the result fields, the Error Codes and an example.
- `dataforge schema <command> <argument> [path]` opens a nested argument one level at a time.
- A flat flag takes a value (`--seed 7`, `--exclude-columns a,b`). A flag shown as `<json>` in `--help` takes inline JSON or `@file.json`. A flag left out means its default.
- A list of records prints as `{"fields": [...], "rows": [[...], ...]}`. Read `warnings` first. `omitted` counts each cut list and names the Operation that returns the rest.
- Results name Operations in snake_case (`list_handles`); the command is the same name in kebab-case (`dataforge list-handles`).

### load
- `dataforge load --path <path>` (background): Read a CSV file into a new frame Handle and report its shape.

### profile
- `dataforge describe-columns --profile <profile>`: Read full column profiles off a profile Handle, flagged columns first.
- `dataforge describe-target --profile <profile> --name <name>`: Read one declared target's problem type and statistics off a profile Handle.
- `dataforge missingness --profile <profile>`: Read how missing values spread across rows, and which columns go missing together.
- `dataforge profile --frame <frame>` (background): Profile a frame once into a profile Handle and return its Dataset Digest.
- `dataforge top-associations --profile <profile>`: List the most strongly associated column pairs off a profile Handle, strongest first.
- `dataforge value-summary --profile <profile> --column <column>`: Read one column's top values, rare labels, bounds and percentiles off a profile Handle.

### split
- `dataforge split --profile <profile>` (background): Split the frame behind a profile into a test frame and folds, each a new frame Handle.

### impute
- `dataforge compose-imputer --recipe <recipe> --units <units>`: Compose a recipe's fitted units into an imputer Handle.
- `dataforge explain-routing --routing <routing>`: Read the stored Routing Evidence behind each column's strategy.
- `dataforge fit-unit --recipe <recipe> --unit-id <unit_id>` (background): Train one unit of a recipe on a frame and return a unit Handle.
- `dataforge impute --imputer <imputer> --frame <frame>` (background): Fill a frame with an imputer into a new frame Handle ready to model on.
- `dataforge resolve-recipe --routing <routing>`: Resolve a routing into a recipe Handle that lists the units to fit.
- `dataforge route --profile <profile>`: Route every column of a profile to an imputation strategy, into a routing Handle.

### evaluate
- `dataforge c2st --reference <reference> --candidate <candidate>` (background): Test whether two frames come from the same distribution with a Classifier Two-Sample Test.
- `dataforge describe-c2st-columns --report <report>`: Read columns' full C2ST results off a c2st Handle, flagged columns first.
- `dataforge evaluate-imputation --profile <profile> --imputed <imputed>` (background): Score how well an imputed frame keeps its data's distribution with a Classifier Two-Sample Test.

### workspace
- `dataforge export-frame --frame <frame>` (background): Write a frame Handle's data as a CSV file in the Workspace and return its path.
- `dataforge list-handles`: List the Workspace's Handles newest first, each with its Lineage and size.
- `dataforge query-frame --frame <frame>` (background): Read raw cells, or measures of them per group, from any frame Handle: a loaded frame, a split fold or an imputed frame.

## Long commands

A command marked (background) costs more as the data grows. On large data, run it in the background or with a longer shell timeout, because a timeout kills a foreground run. `--progress` prints one line per step to stderr. Killing a run is safe: a Handle is written whole or not at all.

## Turning dials

A dial is one threshold inside a command's `--thresholds` JSON; `dataforge schema <command> thresholds` lists them. A result's Dial Pointer (`operation`, `dial`, `value`, `source`) names the dial that decided an outcome, such as a flag on a column. To change that outcome:

1. Read the pointer's `dial` path, such as `thresholds.missingness.severity_high`.
2. Run the command for its `operation` again with the dial set, as in `--thresholds '{"missingness":{"severity_high":0.3}}'`. Dials you leave out keep their defaults.
3. Compare the new Handle's result with the old one's.

Seeds default to a fixed value, so the same call gives the same result.

## Errors

A failure prints a Library Error: `code`, `message`, and fields such as `param`, `issues`, `allowed`, `candidates` and `hint`. Branch on the exit code and `code`, never on `message`.

| Exit | Category | What to do |
|---|---|---|
| 0 | success | Read `warnings`. |
| 2 | InvalidInput | Fix the argument `param` or `issues` names; `allowed` lists accepted values. |
| 3 | UnknownName | Use one of `candidates`. |
| 4 | Conflict | Two declarations contradict: change one of them. |
| 5 | Infeasible | The call cannot run on this data: change the plan or the data. |
| 6 | IncompatibleArtifact | Another library version wrote the Handle: run the command that made it again. |
| 1 | Unexpected | Stop and report `code` and `message`. |

## Workspace Settings

The Operator, the person who set up the library, sets four guardrails in `.dataforge/config.toml` or in env vars: `workspace`, `literal_policy`, `declared_inputs` and `core_budget`. Their flags (`--workspace`, `--literal-policy`, `--declared-inputs`, `--core-budget`) would override the Operator's choice, so leave them out.

- Literal Policy `deny`: fields that hold cell values, such as labels, bounds and percentiles, come back `null` and are listed in `omitted` with reason `literal_policy`. Work from the counts and shares.
- Declared Inputs: once the Operator lists any, `load` reads only those paths and refuses others with `input_not_declared`. Ask the Operator to declare a new file.
- Core budget: the most CPU cores one command uses.
