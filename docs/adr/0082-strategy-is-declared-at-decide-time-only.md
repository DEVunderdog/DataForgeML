# Strategy is declared at decide-time only; plan edits are dial edits

> **Amended by [How units are derived from routing](https://github.com/DEVunderdog/DataForgeML/issues/530) (map #528).** The rule stands, and its reason is restated. After ADR-0088, routing holds no dial base, so "a strategy edit makes the decided hyperparameters stale" no longer applies to it. A `with_strategy` on `ImputationRouting` is still refused, for three reasons: it would leave the column's `signals` contradicting its `strategy`; it would need `mice_model_choice` re-picked when the first column joins MICE; and it would skip exclusion enforcement and the contradictory-config raise (ADR-0077). Units are a projection of routing, so block membership has no edit of its own. The user controls a column's strategy **before routing**: through config (`set_per_column_strategy`, `per_column_constant_fill`, `mnar_columns`, `exclude_columns`) then `route`, or through `author`. Known gap, ticketed separately: config cannot yet force `ClusterConditional` or `GMMSampling`; only `author` can. **Closed by ADR-0095:** `per_column_strategy` accepts both.

`ImputationDecision` shipped three edit methods. Two of them turn dials on a unit that already exists — `with_model_choice` swaps the estimator family, `with_hyperparameters` merges a sparse delta onto the decided base (ADR-0073). The third, `with_strategy`, changed *which units exist*, and that difference was never named. This ADR names it, and deletes `with_strategy`.

The concrete defect: `with_strategy` carried `decided_hyperparameters` through untouched (`_config.py:1743`). Move a column into MICE on a plan that had no MICE block and `_derive_units` emits a `mice` unit whose base is absent, so `_merge_unit_hyperparameters` returns `None`, `_hyperparameters` flattens that to `{}`, and the fitter raises a bare `KeyError` on `hyp["max_iter"]` (`_fitters.py:436`) — far from the edit that caused it. The user cannot repair it either: `with_hyperparameters` validates every key against the decided base, which is empty, so it rejects all of them as keys the unit "has no decided hyperparameter to override" (`_config.py:1842-1848`). A public, documented method could reach a plan that cannot be fitted and cannot be fixed.

The fix is not to teach `with_strategy` to recompute. It is to observe that `decide` already does this correctly, and that `with_strategy` was never load-bearing.

Locked decisions:

- **`with_strategy` is deleted; `per_column_strategy` is the sole declaration surface.** The two were fully redundant, not merely overlapping. They accepted the same strategies — both routed through `_validate_declarable_strategy`, which rejects the same output-only labels with the same redirect strings. They covered the same columns: `_DECLARABLE_STRATEGIES_BY_TYPE` carried an entry for `SemanticType.Numeric` and nothing else, so `with_strategy` rejected every non-numeric column outright, exactly matching `per_column_strategy`'s numeric-only reach. Both set `forced=True`. The only asymmetry was that one of them computed hyperparameters afterwards and the other did not.

- **The dividing rule: structural edits go through `decide`, dial edits ride on the plan.** An edit that changes which units exist invalidates everything derived downstream of the unit list, hyperparameters first. An edit that only changes how an existing unit trains invalidates nothing. `with_model_choice` and `with_hyperparameters` survive because they are on the safe side of that line — and `with_model_choice` is provably safe, since `build_from_choice` constructs estimators from hardcoded constructor arguments and reads no plan hyperparameters at all (`_regression_estimator_factory.py:196-207`).

- **Re-deciding is the replacement, and it is cheap.** `decide` is pure in `(profile, shape, config)` — it never touches a DataFrame and trains nothing (ADR-0060). Re-routing a column is `set_per_column_strategy` followed by a second `decide` call, which recomputes the hyperparameter base *after* the strategy is known. This is the path that was already correct; deleting `with_strategy` makes it the only path.

- **ADR-0071's recovery loop is restated in those terms.** `UnitNotTrainableError` is still caught by the caller, who still re-routes the offending column and refits; the re-route is now a fresh `decide` rather than a plan edit. Nothing about single-track failure changes. Worth recording that the deleted method's own bug never fired on this path: recovery moves *downward* into a scalar strategy, whose unit needs no dials, so the `KeyError` only ever waited in the upgrade direction that recovery does not use.

- **A stored plan is not an editable artifact, so nothing is lost by removing in-place re-routing.** What persistence exists for is the trained model — fitting is the expensive step; deciding is not. A decision is serialised as the glue `compose` needs to rehydrate units against (ADR-0081's no-aggregate-format consequence), and editing a loaded plan's strategies would desync it from the units already fitted under it, which `compose`'s exact-coverage check would then reject. Post-decide structural editing was not merely unnecessary in the persistence case; it was a way to corrupt one. The profile is separately serialisable for anyone who genuinely wants to re-decide later.

- **`_validate_declarable_strategy` and `_DECLARABLE_STRATEGIES_BY_TYPE` are deleted with their only caller.** `set_per_column_strategy` validates independently — output-only labels and fill-less `Constant` — and deliberately does not check semantic type, because at config-declaration time no profile exists to know a column's type from. This is a real reduction in what is checked, and it is accepted: a non-numeric column named in `per_column_strategy` is silently ignored by the router rather than rejected. That silent-ignore predates this ADR and is left as it was found; it belongs to the declaration surface, not to the edit surface being removed here.

Consequences:

- Breaking change to the public plan surface. `ImputationDecision.with_strategy` is gone with no deprecation shim — the library is pre-1.0 in practice and the method's correct uses are all expressible as a second `decide` call.
- ADR-0060's "the plan is immutable" bullet is narrowed: immutability still holds, but the set of edits it describes no longer includes strategy.
- ADR-0066's `forced` field now has exactly one writer, the router. It remains a real field on the plan rather than a parsed signal string, for the reason ADR-0066 gave: a plan loaded from a store must answer "was this forced?" without the originating config.
