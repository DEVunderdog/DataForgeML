# The Operation Catalogue is a Harness file of MCP Tool entries

ADR-0099 said the catalogue data is generated from the Operation files. A Harness uses it for tool search and deferred loading, and the Tool Calls delivery comes from it. This ADR decides what the catalogue is, which fields each entry carries, what the library guarantees about them, and who reads it. The key point is the reader. The catalogue is for the **Harness**. The model never reads it whole. In Code Mode the Agent learns the library from `SKILL.md` and one Operation file at a time (ADR-0108). In Tool Calls the Harness registers entries as deferred tools, and the model loads a few at a time through search. That is the same progressive disclosure as Anthropic's "code execution with MCP" file tree.

## Decisions

- **The catalogue is a generated, committed file at `dataforge_ml/_harness/catalogue.json`.** A test regenerates it and fails on any difference. An `importlib.resources` accessor finds it for Python Harnesses. The `[mcp]` server and the `SKILL.md` Operation index are generated from it. Gained: a Harness in any language can read it without importing the library or starting MCP, and every change shows in review. Given up: one more generated file to keep fresh. The rejected options were a Python-only function and MCP `tools/list` as the catalogue (ADR-0099 refused to make MCP the hub).
- **It stays out of the Agent's path.** It lives under `_harness/`, `SKILL.md` never mentions it, and its top-level `description` says it is for Harnesses. ADR-0108 exposes the whole package directory to the Agent, so the location is the guard. Gained: an Agent following the Skill never meets a file of every schema at once. Given up: a less obvious place for Harness authors, which the accessor and the README cover.
- **Each entry is an MCP `Tool` object.** The model-facing fields are `name`, `title`, `description`, `inputSchema`, `outputSchema` and `annotations`, plus `input_examples`. Library-only fields go in `_meta` under the `dataforge_ml/` prefix. Anthropic's tool format has nowhere for `_meta`, so the mapping drops it, and MCP clients do not show it to the model. Gained: most Harnesses already consume this shape, and Anthropic tool definitions are a cheap mapping. Given up: changes to the MCP spec become ours to follow.
- **`description` is the docstring's summary, `Use when`, `Returns`, `Errors` and `See Also`.** `Parameters` already go into the input schema's property descriptions (ADR-0101). `Example` becomes `input_examples`. Gained: in Tool Calls a tool explains itself as fully as its file does in Code Mode, nothing is said twice, and tool search matches on richer text. Given up: more tokens for each tool a Harness loads.
- **`input_examples` are captured, not written.** While the tested `Example` (ADR-0108) runs, the arguments that reach the Operation boundary are recorded. Gained: an example can never be invalid or stale, and Anthropic measured tool-use examples raising accuracy from 72% to 90%. Given up: one example per Operation, showing fixture Handle ids.
- **Each Operation declares one `effect`: `read`, `create` or `export`.** `read` writes nothing (detail Operations, `explain_routing`, `list_handles`). `create` writes new Handles. `export` writes a file into `exports/`. The MCP hints are derived from it: `readOnlyHint` and `idempotentHint` are true only for `read`, and `destructiveHint` and `openWorldHint` are always false. A test enforces that no Operation deletes anything. Gained: a Harness can auto-approve or run reads in parallel with confidence. Given up: one declaration per Operation, and coarse hints.
- **Cost is one mechanical fact: `scales_with_data`.** It is true when the Operation reads dataset rows (`load`, `profile`, `split`, fit, evaluate, `export_frame`) and false when it reads only stored records. There is no cost tier, because the true cost depends on the data and the routing, and ADR-0099 gives time to the Harness. Gained: a value that is always true as stated, and enough for a Harness to pick timeouts and show progress. Given up: it cannot tell big from huge. That weight lives in the `Use when` prose.
- **`result_budget_tokens` carries each Operation's declared Result Budget.** The catalogue names the tokenizer (`o200k_base`) once at the top. Gained: a Harness can size its output cap per tool from a tested number. Given up: the number is an estimate in a stand-in tokenizer.
- **Preconditions are Handle kinds only.** `consumes` lists the kinds of the Handle arguments and `produces` the kinds made. Both are derived from the typed Handle fields. Finer rules, such as "the profile must have a target", stay as Error Codes, because checking them needs the data. Gained: the whole Operation graph, derived and never stale, and a later test that every consumed kind is produced somewhere. Given up: state rules are not visible before the call.
- **Errors appear twice.** Each entry has `errors`, its hand-written Error Codes, already tested to exist (ADR-0108). The top level has `error_codes`, the whole registry generated from ADR-0100's single source: code, category or `warning`, and hint. Gained: a Harness can map categories to retry policy without reading docstrings. Given up: the top-level table grows with every code.
- **Three grouping and loading hints.** `phase` is a closed enum: `workspace`, `load`, `profile`, `split`, `impute`, `evaluate`. `see_also` lists the Operation names from the docstring. `load_first` marks the 3–5 entry Operations to keep non-deferred (`load`, `profile`, `list_handles`), and the field's definition says the Harness has the final say. Gained: a Harness can namespace tools, preload neighbours and set up deferred loading well. Given up: `load_first` is the library guessing at a Harness's job.
- **`definition_tokens` records each entry's model-facing size, with no cap.** It is the measured size of `name`, `description`, `inputSchema` and `input_examples`. A large definition means the Operation does too much. The fix is to split the Operation, not to trim its text, so no test caps it. Gained: a growing Operation shows in the snapshot diff, and a Harness can use the size when choosing what to defer. Given up: nothing stops an oversized entry from shipping, except review.
- **The top level holds exactly:** `library_version`, `tokenizer`, `description` (addressed to Harnesses), `error_codes`, `handle_kinds` (a closed list with one line each, which `consumes` and `produces` refer to) and `tools`. There is no timestamp, so the file is byte-stable (ADR-0102). Gained: everything a Harness needs to register and route tools sits in one place. Given up: no generation metadata.
- **The Result Budget becomes 10k tokens.** It was 8k (ADR-0102). 10k matches the point where Claude Code warns about an MCP result and stays far under its 25k cutoff. Gained: richer single results, and fewer detail calls. Given up: margin. `o200k_base` can count lower than Claude's tokenizer, so a result right at budget may set off Claude Code's warning.

## Considered Options

- **A Python-only `catalogue()` function, or MCP `tools/list` as the catalogue.** Rejected for the reasons above.
- **A file at the package root, with a "don't read this" note in `SKILL.md`.** Rejected: the note draws attention to the file.
- **A bespoke entry shape.** Rejected: every Harness would have to learn it.
- **Summary-only or whole-docstring descriptions.** Rejected: the first leaves Tool Calls without `Use when`, and the second repeats the parameters.
- **Hand-written argument examples.** Rejected: they can go stale or be invalid.
- **A cost tier.** Rejected: it is a guess that is wrong for some routings.
- **Written-out state preconditions.** Rejected: they need the data to check, and Error Codes already carry them.
- **A token cap per entry.** Rejected: it treats the symptom. An oversized Operation is split.
- **A 16k Result Budget.** Rejected: it sets off Claude Code's 10k warning on every large result and leaves less margin under the 25k cutoff.

## Consequences

- ADR-0102 is amended: the default Result Budget is 10k, not 8k.
- ADR-0099's Harness contract gains a line: the Harness's output cap is at least the largest `result_budget_tokens` in the catalogue.
- `CONTEXT.md` gains **Operation Catalogue**, and its **Result Budget** entry reads 10k.
- New tests: the catalogue is fresh; every `see_also` and `load_first` name is a real Operation; every `consumes` kind is in `handle_kinds`; every `effect` matches what the Operation writes; no Operation deletes anything; `input_examples` validate against `inputSchema`.
