# Model application order is plan order, and the independence rule is a fit-time claim only

ADR-0056 committed to thread-based concurrency governed by an independence rule, and closed with the claim that "concurrency never changes a result: same fixed seeds, same fold splits, executed in parallel." That claim is false as implemented, and the reason is not the one the failing tests suggest. This ADR amends ADR-0056: the thread model and the independence rule survive, but the rule is **a claim about fitting, not about transforming**, and the ordering that transform depends on is now pinned explicitly rather than inherited from thread scheduling.

The mechanism is narrow and was verified by experiment, not by reading. `FittedImputer.transform` applies model-based units as a **chain** — `result_df = unit.transform(result_df)` — so each unit sees the output of the units before it. `regression:c` predicts `c` from `a, b, d, e`; if `regression:d` ran earlier in the chain, `c` is predicted from an *imputed* `d`. The order of that chain is `dict` insertion order over `FittedImputer.models`, and both engines populate that dict **from inside the thread pool** (`_numeric_imputer.py` via the unit closures; `_executor.build()` via `self.fitted_units`). Insertion order is therefore thread-*completion* order. Under `max_workers=4` the order observably shuffles between runs of an identical config; under `max_workers=1` it is stable. Two fits of the same data with the same seed produce imputers that disagree — the parallel path is not reproducible even against itself.

Three plausible explanations were tested and eliminated, and recording them matters because the first was the standing hypothesis: **the `n_jobs_inner = 1 if workers > 1 else -1` rule is not the cause.** Pinning every factory-built estimator to `n_jobs=1` leaves the divergence intact (and merely reshuffles which seeds trip it). The estimator in the failing case is a `BayesianRidge` pipeline with a `linear` tag — `RandomForestRegressor`, the estimator `n_jobs` would affect, never enters. Nor is it sklearn or BLAS: a bare `IterativeImputer` over either estimator is bit-identical across four threads, and pinning `OMP/OPENBLAS/MKL_NUM_THREADS=1` changes nothing. The fitted regression models are byte-identical across runs; only the order in which they are applied differs.

That said, the eliminated hypothesis is **not** a non-issue — it is a *second*, latent violation of ADR-0056's determinism claim, and the two must not be conflated. `RandomForestRegressor` is genuinely not `n_jobs`-invariant: at a fixed `random_state`, `n_jobs=1` and `n_jobs=-1` differ at ~1e-15, which an `IterativeImputer` loop amplifies. So the derivation rule *does* make sequential and parallel fits disagree — but only once a column routes to `RandomForestRegressor` (`ComplexNonlinear` above `gradient_boost_min_rows`), which no current test exercises. The rule and the determinism promise are in direct contradiction wherever that path is live. That tension belongs to the ticket that owns the derivation (#356) and is deliberately not resolved here; this ADR records only that it is real, distinct from the ordering defect, and not to be dismissed as the ordering fix lands.

Locked decisions:

- **Model application order is the plan's unit order.** Both engines compose `FittedImputer.models` in the order units appear in the decision, not in the order threads finish. The plan is already a pure, ordered value (ADR-0060), so an order that is *decided* rather than *raced* costs nothing and is the only order both engines can agree on without coordinating. This exactly reproduces today's `max_workers=1` output — the fix is a pinning, not a behaviour change.
- **The independence rule is a fit-time claim.** ADR-0056's rule — parallelize across units sharing no data dependency — holds for *fitting*: the fitted models are provably order-independent. It does **not** hold for *transforming*, where the chain is a real data dependency between units the rule calls independent. ADR-0056's unqualified "concurrency never changes a result" is narrowed accordingly: concurrency does not change *what is fitted*; ordering changes *what is applied*, and ordering is now decided, not scheduled.

  **Reverted by ADR-0070.** With the chain removed, transform has no data dependency between units either, so the narrowing is no longer needed: ADR-0056's rule stands unqualified at both ends.
- **The chain itself stays.** Each model-based unit continues to consume its predecessors' output. The alternative — every unit reading one pre-model snapshot — is the more principled shape and is deliberately not taken here, because it changes user-visible imputation output and would force the parity gate (#372) to encode invented expectations rather than the legacy behaviour it exists to preserve. Parity-first: pin the order now, argue the semantics separately.

  **Superseded by ADR-0070.** That argument was had once the gate was green, and the snapshot was taken: the chain's "better estimate" advantage was measured across 30 seeds and found to be a coin flip, so nothing weighed against the principled shape. The order pinned here survives — `models` is still composed in plan order — but it is no longer load-bearing on the transform result. Read the "ordering changes *what is applied*" claim below as historical.

## Status

accepted

## Considered Options

- **Feed every model-based unit the same pre-model snapshot and merge per target column.** The genuinely independent shape: it would make ADR-0056's rule true as originally written, and it would remove the train/serve skew described below. Rejected *for now*, not on merit — it changes imputation output for every user with more than one model-based unit, and it cannot land while #372's job is to prove the executor matches the legacy path. It is filed as its own design question rather than foreclosed.
- **Sort `models` by key.** Rejected: it is deterministic but arbitrary — it makes `regression:a` precede `regression:b` for alphabetical reasons, encoding an execution semantic in a column name. The plan already carries a considered order; a second, incidental one would compete with it.
- **Return an `OrderedDict` from the thread pool keyed by submission order.** Rejected as a half-measure: `execute_all_pending` already iterates `futures` in submission order, but `self.fitted_units` is written inside `execute_unit`, so the ordering would hold only for the batch driver and silently break for any caller driving units one at a time — which is precisely what ADR-0061's resumable executor exists to allow.
- **Declare the parallel path non-reproducible and weaken the test.** Rejected outright: reproducibility of a fit is the property ADR-0056 was written to promise, and a library that returns a different imputer on each run of the same seed has no defensible determinism story.

## Consequences

- **The parity gate (#372) becomes possible.** Until the order is pinned, an executor-vs-legacy comparison is racing two independently-shuffled dictionaries; the gate would have been flaky for reasons unrelated to what it was testing. This ADR is a prerequisite for #372, not a follow-up to it.
- **#356's premise is corrected.** Its spec states that units are "independent by construction ... so no sequencing is needed." Fit-time, true. Transform-time, false — sequencing is exactly what is needed, and it now comes from the plan.
- **A train/serve skew is documented and left open.** `fit_regression_unit` trains on the raw train split, where `IterativeImputer` imputes feature nulls with its own internal round-robin; at transform the same model may receive features already imputed by a *sibling* unit (MICE, or another regression). The model therefore serves on a feature distribution it was not trained against. This is pre-existing, is not introduced here, and is the strongest argument for the snapshot option above. **Closed by ADR-0070** — the sibling half of it. The scalar half (a model trained on raw feature nulls serving on scalar-filled features) survives both shapes and remains open.
- **Two engines must now agree on an ordering, which is a coupling.** `FittedImputer` depends on the plan's order being meaningful and stable; a future change that reorders `decision.units` for an unrelated reason silently changes imputation output. The order is load-bearing and must be treated as such. **Made inert by ADR-0070**: the units now merge on disjoint columns off a shared snapshot, so a reorder of `decision.units` cannot reach the result.
- **The concurrency tests stop being flaky for the right reason.** They currently pass in isolation and fail in the full suite, because the session-scoped `rng` fixture makes the fixture data itself depend on test order — a second, independent defect this ADR does not address.
