# Inner parallelism is spent on fitting, never on prediction

ADR-0067 closed by handing an unresolved contradiction to #356: the derivation rule `n_jobs_inner = 1 if workers > 1 else -1` and ADR-0056's determinism promise "are in direct contradiction wherever that path is live," because `RandomForestRegressor` is not `n_jobs`-invariant. This ADR resolves it, and the resolution keeps both — the rule survives intact and determinism becomes stronger than it was, because the contradiction turned out to rest on a false dichotomy.

The measurement that dissolves it: a RandomForest's non-invariance is **entirely in `predict`, not in `fit`**. Tree building draws each tree's seed sequentially from `random_state`, so `n_jobs` decides only which core builds which tree and the forests are byte-identical across the switch (verified: every `tree_.value` array equal). `predict` accumulates the trees into one shared array from a thread pool, so the additions land in thread-completion order and the sum drifts at ~1e-15.

That drift is worse than ADR-0067 recorded, and the extra fact is what forces this ADR rather than merely permitting it. The divergence is not a *difference between* `n_jobs=1` and `n_jobs=-1`; a wide forest is non-deterministic **against itself**. Eight `predict` calls, same fitted model, same input array, disagree. And `n_jobs` is a fitted attribute that pickles with the estimator, so under the rule as written a `max_workers=1` fit does not merely produce a different imputer than a parallel one — it produces a *persisted artifact whose `transform` never settles*, for the life of the artifact. The rule was not trading determinism for speed. It was trading determinism for speed and then failing to deliver reproducibility even to the user who never touched the knob.

Locked decisions:

- **Inner parallelism is spent on fitting and pinned for prediction.** The RandomForest branch of `RegressionEstimatorFactory` is built as a `_CoreInvariantRandomForest`: it fits its forest across `n_jobs` cores and then pins the fitted forest to `n_jobs=1` before returning from `fit`, so every prediction that follows — including the ones `IterativeImputer` makes inside its own round-robin — accumulates serially. Fitting wide and predicting pinned is **bit-identical** to fitting serially (verified through the `IterativeImputer` loop, against a control that reproduces today's defect). The parallelism is kept exactly where the time is: building trees is the expensive half, and accumulating their predictions is the cheap one.
- **The pin lives inside `fit`, not at the call site.** `IterativeImputer` predicts during its own `fit`, long before a caller is handed an estimator back, so a caller-side `estimator.n_jobs = 1` after the fact would be too late to protect the round-robin — which is the loop that amplifies the drift in the first place.
- **The derivation rule from #356 stands unchanged.** `-1` at outer degree one, `1` above it. It is now a pure statement about *which layer spends the cores*, with no reach into the result: one worker fits units back-to-back with wide inner parallelism, more than one fits them side by side with the inner estimator pinned so the layers cannot oversubscribe. `max_workers` is the sole control, and switching it changes wall-clock shape and nothing else.
- **`execute_unit` derives `-1` when driven directly.** A one-at-a-time drive — the resumable path ADR-0061 exists to allow — is an outer degree of one and gets the same wide inner parallelism the batch driver's degree-one case gets. Its previous default of `1` meant such a drive used a single core at *both* layers, which no reading of ADR-0056 asks for.

## Status

accepted

## Considered Options

- **Pin `n_jobs=1` unconditionally and drop the derivation.** The straightforward reading of "determinism wins": `n_jobs_inner` reaches nothing but the RandomForest branch (`BayesianRidge` and `GradientBoostingRegressor` have no `n_jobs`), so pinning it everywhere would make `max_workers` the sole control in the most literal sense — nothing derived, nothing to reason about. Rejected because it pays for determinism with cores it does not need to pay: a plan holding one RandomForest-routed unit would fit single-core at both layers, and the measurement shows that cost buys nothing, since the fit was never the non-deterministic half. It also silently deletes a capability — inner parallelism without outer parallelism is a shape a user may want on purpose, e.g. to keep peak memory to one unit's working set while still using the machine.
- **Keep the derivation and narrow the determinism claim to exclude RandomForest-routed plans.** Rejected on the same grounds ADR-0067 rejected the equivalent move for the ordering defect: reproducibility of a fit is the property ADR-0056 was written to promise. It is additionally worse than it looks here — the artifact is unstable against itself, so this is not a claim that could be narrowed honestly to "parallel and serial may differ." It would have to say the library's output is not reproducible at all where RandomForest routes.
- **Add a config knob trading reproducibility for inner prediction parallelism.** Rejected: with the wrapper there is nothing left to trade, so the knob's only function would be to make the determinism guarantee conditional and force every downstream claim (ADR-0056, the parity gate #372) to qualify itself. This library's configurability principle is about not deciding a user's *thresholds* for them; it is not a mandate to expose a switch whose sole effect is to corrupt an artifact.
- **Set `n_jobs=-1` for the fit and reset it afterwards at the call site.** Rejected as unsound, not merely awkward — see the second locked decision. It protects only the predictions made after the fitter returns, and the ones that matter happen inside it.

## Consequences

- **The RandomForest path is now determinism-tested for the first time.** ADR-0067 noted that no test exercised it, which is why the latent defect survived. The determinism criterion is asserted against a plan that actually routes to RandomForest, so the contradiction this ADR closes cannot silently reopen.
- **A fitted RandomForest predicts on one core, forever.** Prediction is cheap relative to fitting, so this is the right side of the trade — but it is a real ceiling on `transform` throughput for a wide forest over a large frame, and it is not configurable. If that ever becomes the bottleneck, the fix is a deterministic accumulation (fixed-order reduction), not re-exposing `n_jobs`.
- **The tests that pinned `max_workers=1` on both sides "so each derives the same inner `n_jobs`" no longer need to.** That constraint existed to work around exactly this defect; the executor-vs-legacy parity gate is now free to compare engines across worker counts, and the comments asserting a RandomForest's predictions "need not be bit-identical across the switch" are obsolete and are removed.
- **The factory returns a type that is not an sklearn estimator class the user would recognise.** `_estimator_name` special-cases it back to `"RandomForestRegressor"` so fit signals keep naming the `ModelChoice` the plan carries. Anything else that reflects over a fitted estimator's type must do the same, and the wrapper's presence inside persisted joblib payloads makes it part of the serialization surface (ADR-0063) — renaming or moving it breaks load of existing artifacts.
