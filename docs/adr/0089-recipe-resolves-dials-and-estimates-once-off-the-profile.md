# The recipe resolves dials and profile estimates once, off the profile

ADR-0088 moved dials, both hyperparameter maps, the profile estimates and the sentinel maps off routing, and left them homeless. They land in one new layer: `resolve_recipe(routing, profile, config) -> ImputationRecipe`. The recipe is everything a unit needs to train except what training learns — the Recipe half of ADR-0059's Recipe/Learned split, now an object of its own. It is resolved **once, off the profile it is given**, so under the hybrid topology every fold trains the recipe that ships.

## Status

accepted — resolves [Where dial defaults and profile estimates are resolved](https://github.com/DEVunderdog/DataForgeML/issues/531) on map #528. Amends ADR-0062 (dials attach to the recipe, not the unit), ADR-0073 (both maps and `with_hyperparameters` move to the recipe) and ADR-0083 (the facts about the data leave the column decision for the recipe's estimates). Amended by ADR-0091: `mice_min_rows` and `knn_max_features` leave the gate list for the four Feasibility Floor bounds, and `mice_max_nearest_features` becomes a second field read by both routing and the recipe. Amended by ADR-0094: the `n_rows - 1` cap on `n_neighbors` is deleted (sklearn caps each column at its donors), so the recipe reads no row count; `gradient_boost_min_rows` leaves the gate list for four Estimator Bounds. Amended by ADR-0095: `domain_snap_bounds` is also resolved for a BoundedDiscrete column forced to `GMMSampling`, and a forced bimodal column with no profile centres gets `None` estimate fields like a hand-written one.

## Decisions

- **No `n_rows` argument.** The row count is the profile's, as in routing. `n_rows` reaches exactly one dial — the `n_rows - 1` cap on KNN `n_neighbors`, which binds only below 26 rows. Every other dial reads profile statistics, so "resolve per fold" really means "profile each fold". The topology allows that and never does it by default. Given up: fold-exact sizing of that one clamp on tiny frames. Which quantity the clamp reads is #526's.
- **The profile is an argument and is checked for columns only.** A routed column missing from the profile raises, naming it. A profile with the same columns but different rows (routing on dev, resolving on the full frame) is documented, not refused. Given up: that protection. Stamping a profile identity on routing would undo ADR-0088.
- **The recipe holds its routing by value.** A recipe can never be fitted against a routing it was not resolved from, because there is one object to hand over. Routing is still obtainable alone; routing never holds a recipe. Given up: cheap routing edits after resolving. `with_model_choice` means resolving again, and resolving again drops the override delta. The order is fixed: edit routing, resolve, dial.
- **Fields:** `routing`, `decided_hyperparameters` (unit id → full dial row from `_STRATEGY_DIALS`), `hyperparameter_overrides` (the sparse delta), `column_estimates` (column → `ColumnEstimates`: `center1`, `center2`, `feature_cols`, `domain_snap_bounds`, only for columns whose strategy uses them), and `numeric_sentinels` / `string_sentinels` from the profile. `hyperparameters(unit_id)` returns the merge. No units (`derive_units(recipe.routing)`), no config snapshot (every operand is already spent). Custom estimators are not decided here.
- **Estimates stay profile estimates, with a stated leak.** Validation rows influence the centres, the bounds and the feature pick. Each is a seed or a selection, not a fitted parameter: the GMM re-learns its means from `train_df`, and the profile's min/max is the honest domain to snap to. Given up: leak-freedom for these three.
- **Two edits.** `with_hyperparameters(unit_id, dict | None)` keeps ADR-0073's per-key merge and edit-time key check. `with_estimates(column, **fields)` overwrites named fields; it raises on an unknown field or on a column with no estimates. It has no base/delta split, because an estimate has no library default to diff against. Given up: "which estimates did I change" as a query.
- **Config splits into gates and operands, with one shared field.** Routing reads the gates (`mice_min_rows`, `knn_max_rows`, `knn_max_features`, `gradient_boost_min_rows`, `mcar_feature_predictability_threshold`, `bimodal_min_correlated_features`, `bimodal_grouping_variables`). The recipe reads the operands (`base_max_iter`, `mice_correlation_threshold`, `mice_n_nearest_features_min_cols`, `mice_max_nearest_features`, `knn_min_neighbors`, `knn_max_neighbors`, `knn_distance_weight_max_null_ratio`, `knn_distance_weight_max_features`). `bimodal_correlation_threshold` is read by both, deliberately: routing counts correlated features to pick ClusterConditional's branch, and the recipe lists them as `feature_cols`. Two fields could let routing pick the centroid branch on three features while the recipe lists one.
- **GMMSampling's `central_tendency` is deleted.** It rode on the base as a "fact" and no fitter read it.
- **No Events.** The recipe owns no loop.

## Considered Options

- **Resolve per fit set (fold train size, then dev).** Rejected: passing a count moves one clamp on sub-26-row frames; the real per-fold version needs a per-fold profile the topology never makes, and the recipe would then differ across folds from the one that ships.
- **Learn the estimates at fit time from `train_df`.** Leak-free and fold-correct. Rejected: the estimates disappear from inspection, `author`'s authored centres lose their landing spot, and a train-only min/max clips valid values seen only in validation.
- **Take overrides as a `resolve_recipe(..., overrides=)` argument.** Rejected: it breaks ADR-0073's grammar and hides the decided base behind the merge. Its one merit — surviving a re-resolve — matters only if resolving repeats, and it runs once.
- **Name it `configure` / an `ImputationConfiguration`.** Rejected: it collides with `ImputationConfig`, which is user input, not resolved output.
