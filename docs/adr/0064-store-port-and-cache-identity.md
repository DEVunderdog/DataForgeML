# The store is a dumb documents+blobs port; artifacts are content-addressed by a data fingerprint and refused loudly on identity mismatch

ADR-0061 established that an executor is checkpointed as `(plan identity + the set of `done` `FittedUnit`s)` — never a whole pickled builder, and `train_df` is never serialized. ADR-0063 specified the *wire form* of each object that crosses the persistence boundary and the version-gated **reconstruction** contract ("can these bytes be *safely and faithfully* rebuilt under the installed sklearn/numpy/joblib?"). This ADR specifies the sibling half charted for #338: the **abstract store port** the library talks to, the **identity/keying** model that makes resume trustworthy, the **validation-on-load** for *relevance* ("do these bytes still correspond to *my* inputs?"), and how the port stays independent of the deferred service's DB. It is the reference instance of the "storage-agnostic store interface + cache identity" frame in the wayfinder map (#333). The concrete persistence DB (recommended Postgres + JSONB + object storage) and artifact signing remain out of scope.

## The #337 / #338 seam

ADR-0063 owns **reconstruction/correctness** — version gates + the SHA-256 payload checksum; a mismatch there **refuses** regardless of inputs. This ADR owns **identity/relevance** — whether a loaded artifact still matches the *data, config, and library version* it was produced for. The DataForgeML library version appears in both, playing different roles (pickle-compat gate there; cache-invalidation key here); that is expected, not duplication (ADR-0063 already said so). The load-layer runs the 0063 reconstruction checks *and* the 0064 relevance check before any artifact is trusted.

## Locked decisions

- **Content-addressed keying; the key *is* the identity.** An artifact's storage key is `SHA-256(data_fingerprint + config_snapshot + library_version)` (per object kind, see below). A changed input yields a *different key*, so a genuine "my data/config changed" is never a stored-object mismatch — it is a plain **cache miss**, and a miss is normal (cold start → compute). Because profile and decision are deterministic functions of their inputs, a resume regenerates the exact same key from the same inputs; content-addressing gives idempotent writes and structural dedup for free. Each artifact *also* **stamps its own identity** inside its manifest, so a fetched blob can be verified against the key that fetched it — defense-in-depth exactly parallel to 0063's version stamp + checksum. Human-readable / mutable "latest run for dataset X" pointers (a name → hash alias layer) are **deferred to the service**, the same way signing was; the library ships only content addresses.

- **The data fingerprint is a library-computed full-content hash, carried, not recomputed.** Identity binds to a **`data_fingerprint = SHA-256` over the full content** of the Polars frame — *not* a structural (shape/dtype) or statistical (nulls/moments) summary. Those cheaper summaries can **collide** — two genuinely different datasets sharing a shape or moments would alias to the same fingerprint and trigger a false cache hit that silently imputes with a model trained on other data, exactly the unobservable failure the library's **accuracy-over-speed** stance forbids (cf. ADR-0063's refusal of silent numeric drift). The full-scan cost is paid **as a by-product of the Phase 1 profiling pass that already reads the whole frame**: the profiler emits `data_fingerprint`, it is stamped on the profile, and it rides along the profile → decision → `FittedUnit` chain. On resume the user (who **always holds their Polars frame**, a standing assumption) hashes the current frame once to derive the lookup key — the data they had to touch to train anyway — never a re-scan on each store operation. The library computes the fingerprint itself and never trusts a user assertion that "this is the same data."

- **Per-kind identity composition.** The fingerprint is the atom; each object keys on its own distinctive inputs plus the fingerprint and the library version:
  - **Profile** — `hash(data_fingerprint + profiling_config + library_version)`.
  - **Decision** — `hash(profile_identity + config_snapshot + library_version)`; the decision is value-free and depends only on `(profile, shape, config)`, so it binds to data *transitively* through the profile identity.
  - **`FittedUnit`** — `hash(decision_identity + unit_id + data_fingerprint + library_version)`; the fitted unit trained on actual row values, so it binds to `data_fingerprint` **directly** as well as transitively. This direct binding is what the resume relevance check compares against.

- **The store port is dumb: two primitives over opaque keys.** The store knows only **documents** (JSON) and **blobs** (bytes) keyed by an opaque string — `put_document(key, json)` / `get_document(key)`, `put_blob(key, bytes)` / `get_blob(key)`, `exists(key)`. It has no knowledge of profiles, decisions, or fitted units. All serialization (including 0063's manifest-vs-payload split) lives in a thin library layer *above* the port, which turns a `FittedUnit` into one manifest-document + one payload-blob under related keys and hands the store plain bytes. This is what keeps the port **DB-agnostic**: `put_document` → a Postgres JSONB row, `put_blob` → an object-storage object, with no backend understanding DataForge types. No `list`/`delete` in the minimal surface — resume enumerates units from the *plan*, not the store, and content-addressed writes are idempotent; housekeeping graduates to the service. The library ships a default **`LocalFileStore`** (documents as `.json`, blobs as `.bin` under a root dir; key → filename mapped internally so no path semantics leak) so it is usable out of the box.

- **Validation on load: transform never checks; load-for-reuse refuses loudly.** The store validates nothing; the library load-layer runs every trust check. Two moments, two rules:
  - **`transform` (inference)** performs **no** data-identity check. Applying a fitted model to a new, different DataFrame is the whole point of inference; fingerprinting there would be wrong.
  - **Loading fitted state from the store to reuse or resume training** compares the supplied frame's `data_fingerprint` (and config / routing) against the artifact's stamped identity. **Any mismatch raises `ArtifactIdentityMismatchError`** — never a silent retrain, never a mere warning. A fitted model is bound to the rows it trained on; quietly continuing against different data is misleading and forbidden by the library's "no silent fallback for forced work" stance (ADR-0029). A cold **miss** (no artifact at the computed key) is *not* a mismatch — it is a normal first run → compute. A **stamped-identity inconsistency on a present blob** (fetched by key `A`, manifest says `B`) is impossible under content addressing and therefore signals corruption or a wrong-blob store → also **raise**. The 0063 reconstruction checks (version gates + checksum) run alongside and refuse on their own terms.

- **Crash-safety without transactions: the manifest is the commit marker, written last.** A `FittedUnit` is two writes; requiring the port to write both atomically would demand cross-system transactions the filesystem and the future Postgres-row + object-store hybrid cannot provide, killing agnosticism. Instead: **write the payload blob first, then the manifest last.** A reader trusts a unit **only if its manifest exists**, then fetches the payload and verifies the checksum. A crash between the two writes leaves an **orphan blob with no manifest** — invisible to readers, benign, swept by later housekeeping. A manifest never points at a missing or partial payload. This works identically on a filesystem and on object-store + row store.

- **No persisted state machine — state is derived from durable facts.** The store layer keeps **no mutable status record**. "Committed vs orphan" is *derived* from a durable fact (does the manifest exist? does the checksum verify?), so it can never drift from reality the way a stored `writing/committed` field could — and a persisted status field would re-introduce the very atomicity problem the manifest-last discipline solves. The one legitimate state machine — the executor's `pending → running → done` (ADR-0061) — is **rehydrated on resume** by asking the store `exists(unit_key)` for each unit in the plan (present → `done`, absent → `pending`; `running` is transient and never persisted), not read from a second stored copy.

## Status

superseded by ADR-0072

The `ArtifactStore` port, `LocalFileStore`, content-addressed keying, the `data_fingerprint`, load-for-reuse relevance validation (`ArtifactIdentityMismatchError`), and manifest-last crash-safety are removed: with cross-process resume retired (ADR-0071) and the persistence service still deferred, storage becomes the user's business and persistence collapses to bare `serialize`/`deserialize`/`inspect` free functions (map [#377](https://github.com/DEVunderdog/DataForgeML/issues/377)).

## Considered Options

- **Logical-key + stamped identity** (caller-chosen run names; validate stamped identity on load). Rejected as the spine: it needs stale-entry management and a mutable naming layer inside the library; content-addressing gives idempotence and dedup for free, and the naming/alias layer is exactly what the deferred service should own.
- **Structural or statistical data fingerprint** (shape+dtype, or nulls+moments). Rejected: both can collide, and a false cache hit silently imputes with a model trained on different data — the unobservable numeric failure the accuracy-over-speed stance forbids. The full-content hash is collision-proof and is paid inside the profiling scan already underway.
- **User-asserted data identity** (trust the re-supplied frame is "the same" without hashing). Rejected: an accidentally different frame yields a silently wrong reused model; the library computes and checks the fingerprint itself, consistent with 0063's strict posture.
- **Typed high-level store port** (`save_profile`/`load_unit`/…). Rejected: every backend would have to understand DataForge serialization, duplicating the 0063 wire format into each and destroying DB-agnosticism; the dumb documents+blobs port maps cleanly onto JSONB-row + object-storage.
- **Transactional store requirement** (write manifest+payload atomically). Rejected: unachievable across a filesystem or a row-store + object-store split without two-phase commit; manifest-last delivers crash-safety with only benign orphan blobs as the failure mode.
- **Explicit persisted state-tracking machine** for artifacts. Rejected as over-engineering: it duplicates what manifest-presence already encodes, a mutable status can drift from the real bytes, and crash-safely updating that status recurses the original atomicity problem. Revisit only as a *service* concern under multi-writer contention or write-auditing needs.
- **Silent retrain / soft warning on load-for-reuse data mismatch.** Rejected: a fitted model bound to different data must fail loudly; the mismatch is a hard `ArtifactIdentityMismatchError`.

## Consequences

- The Phase 1 profiler gains a `data_fingerprint` output (full-content SHA-256, computed during the existing whole-frame pass) stamped on the profile and carried by the decision and every `FittedUnit`.
- `ArtifactIdentityMismatchError` joins the user-catchable exception set (Public API, ADR-0050), sibling to 0063's `IncompatibleArtifactError` — reconstruction-failure vs relevance-failure.
- The DataForgeML library version (currently `2.2.1`) is the cache-invalidation key here as well as the pickle-compat master key in 0063; the tight-pins/lockfile work that guarantee it (the dependency-freshness sibling ticket) matter for this contract too.
- Crashes accumulate orphan payload blobs with no manifest; a local sweep (and, later, service-side GC) is the housekeeping story — deliberately out of the minimal port surface.
- The map (#333) "Decisions so far" gains the #338 line; the naming/alias layer and multi-writer status-tracking are inherited by the deferred service, alongside the concrete DB and signing.
